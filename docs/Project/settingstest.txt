Why so many subsections are reported “missing”
- Strict header matching: the test requires an exact match of the three-line header block format:
  //
  // SUBSECTION NAME
  //
  - Any small name change (plural vs singular, extra words, abbreviated titles) causes a mismatch. For example: "Planner settings" vs "Planner Motion" or "Hotend Offset" vs "Hotend Offsets".
- Conditional compilation: some subsections exist only when certain feature macros are enabled. If `save()`/`_load()` wrap a block in a different set of `#if` conditions than the struct, the script will see different subsections at parse time for the active configuration.
- Duplicates or extra headings: `save()` and `_load()` include additional grouping headings (e.g., "Planner Motion", "Probe XYZ Offsets", "PROBE ACTIVATION Calibration") that don't match the exact struct headings — these produce extra entries in `save()`/_load.

Which differences are likely real bugs vs. cosmetic
- Cosmetic / test-artifact:
  - Header name synonyms, whitespace, pluralization and i18n-style differences — cause false positives in the strict test.
  - Extra/duplicate headings in `save()`/_load()` that are purely organizational and do not change the order of EEPROM writes relative to struct fields.
- Real / dangerous:
  - Subsections that contain the same fields but are placed in a different order relative to the struct. That is exactly what we see with the M905/probe fields: their struct declaration is earlier (in `HAS_BED_PROBE`) while the actual EEPROM writes for those fields are later under `PROBE ACTIVATION Calibration`.
